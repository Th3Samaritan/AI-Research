Field Guide · part 2

Count every byte. Then watch attention shrink them.

One running example throughout: Qwen3-8B, your baseline. First we count its memory by hand until every gigabyte has a name. Then we rebuild attention starting from plain multi-head attention, and change one thing at a time: GQA, MQA, MLA, sliding windows, DeepSeek Sparse Attention, linear attention. Each step comes with real numbers.

The two numbers to keep in your headMemory you need = weights + KV cache + buffers. Bytes read per token = active weights + the KV cache so far. The first decides whether the model fits. The second decides how fast it runs. Every trick on this page shrinks one or both of them.
1 · Memory

Weights, byte by byte

A "parameter" is one number in a matrix. A model file is just its matrices. Count the matrices, multiply by bytes per number, and you have the size. No guessing.

Read the receipt like thisq_proj 4096 × 4096 means 4096 inputs → 32 heads × 128 dims = 4096 outputs. k_proj and v_proj output only 8 × 128 = 1024. That smaller number is GQA: Qwen3-8B has 32 query heads but only 8 key/value heads. The MLP (gate, up, down) is about 78% of each layer.

2 · Memory

The KV cache, by hand

For every token already processed, every layer keeps that token's key vector and value vector, so they never have to be recomputed. Each factor below is a slider. Change one and watch the chain multiply out.

Why each factor is there

  • × 2: one K vector and one V vector. K is what gets matched against queries. V is what gets mixed into the output.
  • × KV heads × head dim: the width of K (and of V) for one token in one layer. Qwen3-8B: 8 × 128 = 1024 numbers.
  • × layers: every layer has its own attention with its own K and V. Nothing is shared between layers (Gemma 3n is an exception).
  • × tokens: one entry per token in the conversation, both prompt and answer. It grows by one entry on every step.
  • × users: every conversation has its own cache. The weights are shared. This is why a server with 100 users needs far more memory than the model itself.

4 · Memory → speed

How memory turns into tokens per second

To produce one token, the GPU has to stream every active weight and the whole KV cache so far from memory into its cores. Count the bytes, divide by bandwidth, and you get a time per token. Here is the arithmetic for Qwen3-8B Q4_K_M on an RTX 4090.

The curve falls because the KV term grows with every token while the weight term stays fixed. At long context the cache, not the model, is what you are waiting on. That is exactly what GQA, MLA, sliding windows, DSA and linear attention attack. The 0.75 factor is typical achieved bandwidth.

5 · Attention from zero

Multi-head attention, with real numbers

A toy model small enough to show every number: 5 tokens, an 8-dimensional residual stream, 4 query heads of 2 dimensions each. Pick which token is "speaking" (the query), and switch how many K/V heads exist. That switch is the whole difference between MHA, GQA and MQA.

K/V heads
    What is stored in the KV cache for these 5 tokens

    What multi-head attention is doing

    • Query = "what am I looking for?" Key = "what do I contain?" Value = "what do I hand over if picked?"
    • Score = q · k ÷ √head_dim. A big score means "relevant". Softmax turns the scores into weights that sum to 1. The output is a weighted mix of V vectors.
    • Several heads let the model look for different things at once. One head might track the subject, another the previous word. Each head has its own q.
    • In MHA each head also has its own K and V, and that is what fills memory. Ask whether the heads really need separate keys. They mostly don't, which is where GQA comes from.

    7 · GQA & MQA

    Grouped-query attention, practically

    The idea in one picture

    Picture 32 students (query heads) studying from textbooks (K/V heads). In MHA every student has a personal copy: 32 books. In GQA-8, groups of 4 students share a book: 8 books. In MQA everyone shares one book. Each student still asks their own question. Only the books are shared.

    What it saves, and what it does not

    • Saves memory: KV cache ÷ (query heads ÷ KV heads). Qwen3-8B: 32 ÷ 8 = 4× smaller than MHA.
    • Saves time: decode is memory-bound, so reading 4× fewer KV bytes makes long-context steps up to 4× faster in the attention part.
    • Does not save compute: every query head still computes a score against every key. FLOPs are identical. The GPU just reuses each loaded K for 4 heads, which raises arithmetic intensity 4×.
    • Saves a little weight: k_proj and v_proj shrink from 4096×4096 to 4096×1024. That is 25 M fewer weights per layer in Qwen3-8B.
    • Costs a little quality: heads in a group can no longer look for different keys. The GQA paper found that 8 groups give quality close to MHA, while 1 group (MQA) degrades noticeably at scale. [GQA, Ainslie 2023]

    The actual code

    # Qwen3-8B shapes, one layer, decoding 1 new token
# x: [1, 4096]
q = x @ Wq      # [1, 4096] → 32 heads × 128
k = x @ Wk      # [1, 1024] →  8 heads × 128  ← only this is cached
v = x @ Wv      # [1, 1024] →  8 heads × 128  ← and this
cache_k.append(k); cache_v.append(v)

# share each KV head with 4 query heads (no copy in fast kernels)
K = repeat_kv(cache_k, n_rep=32 // 8)   # [T, 32, 128] view
V = repeat_kv(cache_v, n_rep=4)

scores = (q @ K.T) / sqrt(128)          # [32 heads, T]
out    = softmax(scores) @ V            # [32, 128] → [1, 4096]
out    = out @ Wo

    8 · DeepSeek

    Multi-head Latent Attention (MLA)

    GQA saves memory by making heads share keys, and pays for it in quality. DeepSeek asked a different question: what if each token stored one small compressed vector, and every head rebuilt its own full K and V from it when needed? You get MHA-like quality with a cache smaller than GQA's.

    # DeepSeek-V3 shapes (hidden 7168, 128 heads)
c_kv  = h @ W_DKV        # [7168] → [512]   ← CACHED
k_rope= rope(h @ W_KR)   # [7168] → [64]    ← CACHED (shared by heads)
# per head i, rebuilt on the fly, never stored:
k_i   = c_kv @ W_UK[i]   # [512] → [128]
v_i   = c_kv @ W_UV[i]   # [512] → [128]

# the "absorption" trick: never even build k_i
score_i = q_i · (W_UK[i] c_kv)  =  (W_UK[i]ᵀ q_i) · c_kv
#        fold W_UK into the query once, then dot with the 512-d latent

    Why it works

    • The 128 heads' keys are highly redundant. A 512-number summary carries almost everything they need, so it is a learned compression.
    • Absorption means decode never expands the latent. Each head's query is projected into the 512-d latent space once, and scores are dot products with the cached latents directly.
    • Why the separate 64-d RoPE key: RoPE rotates keys by position, and a rotation sitting between W_UK and c_kv breaks the absorption trick. So position goes in a small separate key that all heads share, and the latent stays position-free.
    • Cost: more matrix work per step. That is fine, because decode had spare compute and was short on bandwidth.
    • Engine cost: MLA needs dedicated kernels. GQA works with any FlashAttention build, which is why MLA support arrived later in llama.cpp and other engines.
    9 · Gemma

    Sliding-window attention

    A different axis entirely. Instead of making each token's entry smaller, keep only the most recent W tokens in most layers. Gemma 3 and 4 use a 1024-token window in 5 of every 6 layers. The 6th layer is global and still sees everything.

    How information still travels far

    • Every 6th layer is global, so any token can reach any other through those layers.
    • Windows also stack: layer 1 sees 1024 back, and layer 2 sees 1024 back from tokens that already saw 1024 back. The reach grows layer by layer.
    • In practice local layers handle grammar and nearby context, and global layers handle "what did the document say 50 pages ago". The Gemma 3 report found perplexity barely moved when the window shrank from 4096 to 1024.
    • The cache for a local layer is a ring buffer: token 1025 overwrites the slot of token 1.
    10 · DeepSeek V3.2

    DeepSeek Sparse Attention (DSA)

    Everything so far shrank how much is stored. DSA shrinks how much is read and computed per step. A tiny, cheap "lightning indexer" scores every past token. Then the real attention (MLA) runs only on the top 2048.

    One decode step at 128K context

    200 of the past tokens drawn
    Indexer score (computed for every token, cheap)Selected: full MLA attention runs on these
    # per decode step, per layer
# 1) lightning indexer: 64 tiny heads, FP8, one shared 128-d key per token
I[s] = Σ_j  w_j · relu( q_idx[j] · k_idx[s] )   for every past s
# 2) pick the winners
S = topk(I, k=2048)
# 3) normal MLA attention, but only over S
out = MLA(q, c_kv[S], k_rope[S])

    The catch: memory does not shrink

    • DSA still stores every token's latent, because a token ignored now may be selected later. The cache is the same size as plain MLA.
    • What drops is the work per step: the indexer reads 128 bytes per token instead of 1,152, and full attention touches only 2048 tokens.
    • Prefill goes from O(n²) to roughly O(n·k), which is why 128K-token prompts got much cheaper.
    • DeepSeek-V4 goes further and compresses the cache itself along the sequence axis (CSA/HCA). Its card reports 10% of V3.2's KV cache at 1M tokens.
    11 · Qwen3-Next / 3.5 / 3.6

    Linear attention: no cache at all

    Gated DeltaNet replaces "store every key and value" with one fixed matrix per head that is updated in place every token. Memory stops growing with context. Qwen3.5 uses it in 3 of every 4 layers and keeps full attention in the 4th for precise recall.

    What the state is, concretely

    • Per head, S is a 128 × 128 matrix (keys × values). Think of it as a lookup table compressed into a matrix: S·q retrieves the value associated with keys similar to q.
    • Write: the delta rule first reads what S already returns for key k, then corrects it toward v. Old associations get overwritten instead of piling up.
    • Forget: gate α (between 0 and 1) fades everything a little each step, so stale context decays.
    • Limit: 16K numbers per head cannot hold a perfect copy of a 100K-token book. Exact quoting and needle-in-a-haystack recall need the real attention layers, hence the 3:1 hybrid.
    # Gated DeltaNet, one head, one new token (Qwen3.5-9B sizes)
# S: [128 x 128] float32  ← the whole "cache" for this head
k = l2norm(x @ Wk)        # [128]
v = x @ Wv                # [128]
q = l2norm(x @ Wq)
a = sigmoid(x @ Wa)       # forget gate α
b = sigmoid(x @ Wb)       # write strength β

S = a * S                       # fade
S = S + b * outer(v - S @ k, k) # delta rule: fix what k maps to
o = S @ q                       # read
