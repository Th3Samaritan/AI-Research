Kernels & vLLM: how the math becomes speed

The architecture (parts 2–4) says what to compute. Kernels decide how fast one GPU does each piece. Engines like vLLM decide what to compute when for many users at once. Benchmarks tell you whether all of it works. This page follows a request through all five layers, with numbers for your hardware.

1 · Kernels

What a kernel is: one recipe, run by thousands of cooks at once

A kernel is one GPU function, such as "multiply this matrix" or "do attention". A forward pass of Qwen3-8B launches several hundred of them.

The hardware it runs on

  • SMs (streaming multiprocessors): the GPU's cores. The RTX 4090 has 128, the H100 has 132. Each SM has tensor cores (matrix-multiply units) and a small, very fast SRAM (shared memory / L1, roughly 100–228 KB per SM).
  • HBM / GDDR: the big, slow memory (24–80 GB) that holds the weights and KV cache. It's slow compared with SRAM: about 1–3 TB/s, versus tens of TB/s in aggregate SRAM bandwidth.
  • A kernel launch splits the work into thread blocks, one or more per SM. Each block loads a tile of data from HBM into SRAM, computes on it with the tensor cores, and writes the result back.

Analogy

HBM is the warehouse, SRAM is each cook's countertop, tensor cores are the cooks' hands, and the kernel is the recipe card handed to all 128 kitchens. Trips to the warehouse are what take the time.

The three rules of a fast kernel

  1. Touch HBM as little as possible: load each byte once and reuse it from SRAM.
  2. Keep every SM busy: enough blocks, balanced across SMs.
  3. Launch few kernels: each launch costs a few microseconds of CPU/driver time, and hundreds per token add up. That's why fusion and CUDA graphs exist.

Where kernels come from

Hand-written CUDA (FlashAttention, Marlin), CUTLASS/CuTe templates, Triton (Python-like GPU kernels; vLLM's fused MoE is written in it), vendor libraries (cuBLAS for GEMMs), and torch.compile, which fuses small ops automatically. llama.cpp writes its own for CUDA, Metal, Vulkan and CPU SIMD.

2 · Roofline

The roofline: is this kernel waiting on memory or on math?

Every kernel's time ≈ max(bytes ÷ bandwidth, FLOPs ÷ peak). Arithmetic intensity, FLOPs per byte, says which one wins.

The rule

Arithmetic intensity I = FLOPs ÷ bytes moved from HBM. The device's ridge point is peak FLOPs ÷ bandwidth. Below the ridge, a kernel is memory-bound: faster math won't help, only fewer bytes will. Above it, the kernel is compute-bound.

Why decode is memory-bound

Generating one token multiplies every weight by a single vector: 2 FLOPs per weight (multiply + add), and each BF16 weight is 2 bytes. So I ≈ 1 FLOP/byte, about 100× below a modern GPU's ridge. The tensor cores sit mostly idle while HBM streams weights. That's part 1's whole speed equation, seen from the kernel's side.

Why quantized weights help decode, but less for prefill

4-bit weights move 4× fewer bytes, so a memory-bound GEMV gets up to ~4× faster, provided the kernel dequantizes inside SRAM (Marlin, llama.cpp's MMVQ). A compute-bound prefill GEMM gains little from fewer bytes unless the math itself runs in lower precision (FP8/INT8 tensor cores).

Analogy

A kitchen where the cooks can chop 100 onions per second but the delivery truck brings only one per second. Hiring faster cooks changes nothing. Bring more onions per trip (batching), or smaller onions (quantization).

3 · Fusion

Kernel fusion and FlashAttention: never write what you can keep

Same math, far fewer HBM bytes. FlashAttention never stores the N×N score matrix, which makes long prompts feasible.

The problem

Textbook attention runs as separate kernels: S = QKᵀ (written to HBM) → softmax(S) (read, written back) → P·V (read again). For an N-token prompt the score matrix S is N × N per head. At long N, those reads and writes dwarf the useful work.

How FlashAttention works

  1. Split Q into row blocks and K, V into column blocks that fit in SRAM.
  2. For one Q block, stream every K/V block through SRAM and compute that tile of scores.
  3. Online softmax: keep a running max and a running sum per row, so the earlier partial outputs can be rescaled when a larger score appears. Softmax never needs the whole row at once.
  4. Accumulate P·V in SRAM, and write only the final output (N × d) to HBM.

HBM traffic drops from O(N²) to roughly O(N·d) per pass. FLOPs are unchanged (slightly more, for the rescaling). FlashAttention-2 reaches 50–73% of A100 peak; FlashAttention-3 reaches about 75% of H100 FP16 peak.[FA2][FA3]

Decode needs a different split: Flash-Decoding

With one query token, FlashAttention would occupy only a few SMs (one block per head). Flash-Decoding splits the cache across SMs, so each SM handles a chunk of past tokens, and then merges the partial softmaxes. All SMs share the cache read.[Flash-Decoding]

Other fusions every engine does

  • Residual add + RMSNorm in one kernel (one read, one write instead of three).
  • SiLU(gate) × up fused into one kernel, often into the GEMM's epilogue.
  • RoPE applied inside the QKV or attention kernel.
  • Dequantize inside the GEMM: 4-bit weights are expanded in SRAM and never written back as BF16 (Marlin, GGUF kernels).

Analogy

Naive attention: chop all vegetables, carry them to the warehouse, bring them back to season, carry them back, bring them back to cook. FlashAttention: chop, season and cook one tray at a time on the countertop, and only plates go to the warehouse.

4 · Architecture → kernels

Every architecture feature needs a kernel before it's fast

This is why a new architecture can be "supported" in an engine and still slow for months. The math runs on generic kernels until a specialized one is written. When you read an architecture paper, ask: which kernel makes this fast, and does my engine have it?

5 · Batching

Batching: the closest thing to a free lunch

Reading the weights once and using them for B tokens costs almost the same as for one token, until you reach the ridge or run out of KV memory.

Why it works

One decode step reads all the weights (W bytes) plus each user's KV cache. With B users in the same step, the weights are read once and multiplied by B vectors (a GEMM instead of B GEMVs). Arithmetic intensity rises to about B FLOPs/byte. Step time grows slowly, so total throughput grows almost linearly with B.

What stops it

  • The ridge: past roughly ridge-point users, weight GEMMs become compute-bound and step time grows with B.
  • KV memory: each user's cache must fit (parts 2 and 4). Usually this limit comes first.
  • KV bandwidth: each user's cache is still read once per step, and batching doesn't share it. At long contexts the cache dominates and the free lunch shrinks.
  • Latency: each user's token arrives once per step, so bigger steps mean slower tokens per user.

Analogy

A bus. The trip costs about the same with 1 passenger or 50 (the weights). Each passenger's luggage (their KV cache) still has to be loaded, and the bus has only so much trunk space (VRAM).

6 · vLLM's core idea

PagedAttention: virtual memory for the KV cache

Store the cache in small fixed-size blocks, allocated as tokens arrive. Waste drops from most of the memory to almost none, so many more users fit.

The problem

Before vLLM, servers reserved one contiguous slab per request, sized for the maximum possible length, because they couldn't know how long the answer would be. Most of each slab stayed empty, and leftover gaps between slabs couldn't be used. The vLLM paper measured existing systems using only about 20–38% of KV memory for real tokens.[Kwon 2023]

How it works

  1. Split GPU KV memory into blocks of 16 tokens.
  2. Each request has a block table: a list of physical block IDs in logical order. It's like an operating system's page table.
  3. A new block is allocated only when the last one fills, so waste is under one block per request.
  4. The attention kernel follows the block table to gather K/V from scattered blocks. That kernel is the "PagedAttention" part.
  5. Blocks can be shared: requests with the same system prompt point to the same blocks (prefix caching), copied on write.

Analogy

A restaurant that used to reserve a 12-seat table for every party "in case more friends come". PagedAttention seats people at 2-seat tables wherever there's room and keeps a note of which tables belong to which party.

Evidence

The paper reported 2–4× higher throughput than FasterTransformer and Orca at the same latency, with near-zero KV waste.[Kwon 2023]

The price

  • The attention kernel must gather from scattered blocks: a little indirection per block. Block size trades indirection overhead against waste.
  • When memory runs out, the engine must preempt a request: swap its blocks to CPU or recompute them later. A latency spike for that user.
7 · vLLM's scheduler

Continuous batching: never let a finished seat sit empty

Re-form the batch at every single step. New requests join immediately and finished ones leave, so the GPU stays full.

The problem

Static batching collects B requests, runs them until the longest finishes, then starts the next batch. Short answers wait for long ones, and new arrivals wait for the whole batch.

How it works

  1. At every step the scheduler looks at the waiting queue and admits requests while KV blocks are free.
  2. New requests are prefilled. With chunked prefill, a long prompt is split into chunks mixed with other users' decode tokens, under a per-step token budget, so running users don't freeze.[Sarathi-Serve]
  3. Every running request gets one token, and finished requests free their blocks at once.

This idea, iteration-level scheduling, came from Orca.[Orca 2022] vLLM combined it with paged memory.

Analogy

A bus that waits until the last passenger gets off before boarding anyone new, compared with a bus that picks people up and drops them off at every stop.

8 · Other engine tricks

What else an engine does, and what each one buys

CUDA graphs

Problem: a decode step launches hundreds of small kernels, and at a few µs each the CPU can't keep up. With batch 1 on a fast GPU, the GPU idles between launches.
Fix: record the whole step once, then replay it with a single launch. vLLM captures graphs for common batch sizes.
Effect: often a double-digit % gain in small-batch decode. Price: fixed shapes, extra memory per captured size, and slower startup.

Prefix caching

Hash each full KV block by its tokens. A new request whose prompt starts with the same blocks (system prompt, few-shot examples, a long document) reuses them, so that part of prefill is skipped. SGLang generalizes this with a radix tree of prefixes (RadixAttention).[SGLang] Effect: much shorter time to first token (TTFT) on repeated context.

Speculative decoding

A cheap drafter (a small model, EAGLE heads, or DeepSeek's MTP layer) guesses k tokens, and the big model checks all k in one forward pass, which costs about the same as one memory-bound decode step. With acceptance rate α, each step yields on average (1−αk+1)/(1−α) tokens.[Leviathan 2023][EAGLE]

Tensor / pipeline / expert parallel

Tensor parallel (TP): split every matrix across GPUs, so each reads 1/N of the weights. It needs an all-reduce twice per layer, so fast links (NVLink) matter. Pipeline parallel: split the layers instead; less communication, but bubbles at small batch. Expert parallel: put different experts on different GPUs and exchange tokens with all-to-all (DeepEP). GQA with 8 K/V heads splits cleanly at TP = 8 (part 4).

9 · Benchmarking

How serving speed is measured, and why one number is never enough

Users feel latency, owners pay for throughput, and you can only trade one for the other. A benchmark sweeps the load and reports both.

The metrics

  • TTFT (time to first token): queueing + prefill. It's what users feel as "it started answering".
  • TPOT / ITL (time per output token / inter-token latency): the gap between tokens while streaming. 1 ÷ TPOT is the per-user tokens/s.
  • E2E latency = TTFT + TPOT × (output tokens − 1).
  • Throughput: output tokens/s (or requests/s) summed over all users.
  • Percentiles: report p50 and p99. Averages hide the unlucky users.
  • Goodput: requests per second that meet a service-level objective (SLO), such as TTFT < 2 s and TPOT < 100 ms.[DistServe] This is the honest capacity number.

The method

  1. Fix the workload: prompt and output length distributions (or a real dataset), plus the arrival pattern.
  2. Warm up (CUDA graphs, caches), then measure.
  3. Sweep the request rate from low to past saturation, and plot latency against throughput. The knee is where latency explodes.
  4. Report everything: GPU, driver, engine version, flags, quantization, max context.
  5. Check quality: a faster setting that drops accuracy isn't a win (perplexity, lm-eval).
  6. Profile where time goes: Nsight Systems for the timeline (gaps = launch overhead), Nsight Compute for per-kernel bandwidth vs peak.

Analogy

Testing a highway: you don't report "cars per hour" at 3 a.m. You ramp up traffic and record both the flow and the travel time, and the capacity is the flow just before the jam.

10 · Sanity check

Is my benchmark number good? Compare it with the roofline

For single-user decode, the ceiling is bandwidth ÷ bytes per token. Divide your measured tok/s by that ceiling, or multiply measured tok/s by bytes per token and compare with peak bandwidth. That's the achieved bandwidth: how well the kernels and engine use the hardware.

  • ≥ 70% of peak: excellent. The kernels are near the roofline, so only fewer bytes (quantization, MLA, MoE) will help.
  • 40–70%: normal for small models or long contexts. Check CUDA graphs and the attention kernel.
  • < 40%: something's wrong: CPU launch overhead, PCIe offload (layers on CPU), a dequantize-then-GEMM path, or a debug/eager mode.

The same check works for prefill, against peak FLOPs: measured prompt tok/s × 2 × active parameters ÷ peak FLOPs.

11 · Your plan

A benchmark plan for Qwen3-8B on Dahir's server

Run these in order. Each step answers one question, and together they tell you which engine and which quantization to use for which job.

  1. Baseline single-user speed (llama.cpp): how fast is one user, at short and long context? 
    llama-bench -m Qwen3-8B-BF16.gguf   -ngl 99 -p 512,2048 -n 128 -r 5
llama-bench -m Qwen3-8B-Q4_K_M.gguf -ngl 99 -p 512,2048 -n 128 -r 5
# newer builds: add -d 0,8192,32768 to measure decode with an already-filled context
  2. Check it against the roofline: put the tg128 number into section 10. Below about 60% of peak bandwidth, investigate before going further.
  3. Quality of each quant: is Q4 still good enough? 
    llama-perplexity -m Qwen3-8B-Q4_K_M.gguf -f wiki.test.raw -ngl 99
lm_eval --model vllm --model_args pretrained=Qwen/Qwen3-8B --tasks gsm8k,mmlu --batch_size auto
  4. Serving capacity (vLLM): how many users, at what latency? 
    vllm serve Qwen/Qwen3-8B --max-model-len 32768 --gpu-memory-utilization 0.90
# in another terminal: sweep the load (repeat for request rates 1, 2, 4, 8, 16, inf)
vllm bench serve --model Qwen/Qwen3-8B --dataset-name random \
  --random-input-len 2048 --random-output-len 256 --num-prompts 300 \
  --request-rate 4 --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,99
  5. Offline throughput ceiling: the maximum tokens/s with no latency target. 
    vllm bench throughput --model Qwen/Qwen3-8B --input-len 2048 --output-len 256 --num-prompts 500
  6. Where the time goes (profile one decode run): 
    nsys profile -t cuda,nvtx -o qwen3_decode \
  vllm bench latency --model Qwen/Qwen3-8B --batch-size 1 --input-len 1024 --output-len 64
    Open the trace and look for gaps between kernels (launch overhead) and which kernels take the most time (GEMMs, attention, sampling).
  7. Write it up: plot latency against throughput per engine and quant, mark the SLO, and report goodput. That's the decision table for the team.
