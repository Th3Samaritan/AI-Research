Why your model makes N tokens per second

Producing one token means reading every active weight once. When you run on your own machine (one user, one request at a time), speed is set mostly by memory bandwidth, not by how many operations the chip can do. Nearly everything on this page follows from that.

01 · Architecture

Anatomy of a token

A decoder-only transformer is a stack of identical blocks around one "residual stream" vector per token. Each block has a mixing step (attention, or a linear-attention variant) and a thinking step (feed-forward MLP, or a mixture of experts). Pick a model to see how its stack is built.

One glowing pulse = one token's trip up the stack

One forward pass, step by step

  1. Tokenize. Text → integer IDs. Qwen3 has a 151,936-entry vocabulary, Qwen3.5 has 248,320, Gemma has 262,144.[8][10][27]
  2. Embed. Each ID picks one row of the embedding matrix, giving a vector of size hidden (4096 for Qwen3-8B). This is the residual stream.
  3. RMSNorm → attention. Project to Q, K, V. Rotate Q and K by position (RoPE).[16] Score the new token against every cached K, softmax, take a weighted sum of the V's, project back, and add to the stream.
  4. Store K, V. The new token's K and V get appended to the KV cache, so earlier tokens never have to be recomputed.
  5. RMSNorm → MLP. SwiGLU: down( silu(gate·x) ⊙ up·x ).[18] In Qwen3-8B this is 3 × 4096 × 12288 ≈ 151 M weights per layer, which is 78% of each block.
  6. Repeat for all layers (36 in Qwen3-8B).
  7. LM head. Final norm, then multiply by a vocab × hidden matrix to get a logit for every token. Sample one (temperature, top-p…), append it, and go back to step 2.

Where the time goes

  • Prefill (reading your prompt): all prompt tokens go through together. Each weight read is reused across hundreds of tokens, so the GPU's arithmetic units become the limit. This phase is compute-bound.
  • Decode (writing the answer): one token at a time. Every weight is read for just 2 FLOPs (a multiply and an add), so arithmetic sits idle waiting on memory. This phase is memory-bound.[43]
  • That is why a 1,000-token prompt can take half a second to read while each answer token takes 20 ms.
  • Attention cost grows with context: each new token reads the whole KV cache. Linear attention (Qwen3.5) and sliding windows (Gemma) exist to cap that cost.

Arithmetic intensity

FLOPs done per byte read. At batch 1 with BF16 weights that is 1 FLOP/byte. An RTX 4090 needs about 165 FLOP/byte before its math units are the limit. The remaining 99% of its compute sits idle during decode.[44]

Why servers batch

32 requests decoding together share each weight read, so intensity goes up 32×. Total throughput rises almost linearly until compute runs out. Move the batch slider to watch it. This is what vLLM's continuous batching takes advantage of.[33]

Why MoE is fast

Qwen3-30B-A3B stores 30.5 B weights but reads only 3.3 B of them per token. Memory needed follows the total. Speed follows the active count.[7]

03 · Hardware

Why a GPU, and how it still runs on a CPU

A GPU is a bandwidth machine

  • Bandwidth: GDDR6X/HBM delivers 1–3.3 TB/s. A desktop's DDR5 delivers 60–90 GB/s, 10–40× less. For decode, this is the main reason GPUs win.
  • Tensor cores: they do 16×16 matrix tiles per instruction, reaching hundreds of TFLOPS. That makes prefill and batching fast.
  • Training really does need GPUs: it is compute-bound with huge batches. Inference at batch 1 does not.

What makes CPUs viable

  • Quantized kernels. llama.cpp stores weights in 4–6 bit blocks and quantizes activations to 8-bit on the fly. It then does integer dot products with SIMD (AVX2, AVX-512 VNNI, ARM NEON dotprod/i8mm), unpacking each block in registers. A full FP16 copy is never created.[38][39]
  • RAM is cheap. 64 GB of DDR5 costs about the same as an 8 GB GPU. Large MoE models fit, and their small active count keeps them fast enough.
  • mmap. The GGUF file is memory-mapped, so the OS pages weights in on demand and you get near-instant load.
  • Threads hit a wall. Decode saturates RAM bandwidth with about 4–8 cores. More threads help prefill (compute) but not decode.
  • Partial offload (-ngl): put as many layers as fit on the GPU and the rest on the CPU. Total time = GPU part + CPU part, so the slow side dominates.

What "requires X GB" actually counts

When llama.cpp or Ollama refuses to load, the number it reports is the sum of three buffers:

05 · Compression

Quantization: trading precision for bytes

Quantization stores each weight in fewer bits, plus a shared scale per small block. What you saw on Qwen3-1.7B (smaller, faster, a bit dumber) is the rounding error below, repeated across 1.7 billion weights.

Why quality drops, and when it drops fast

  • Rounding noise adds up. Each layer's output picks up small errors, and 36 layers compound them. Logits shift, and close calls between tokens flip.
  • Outliers ruin blocks. One large weight stretches the scale, so the other 31 get squeezed into a few levels. Try the button above. A few activation channels in LLMs are 100× larger than the rest.[37]
  • Small models suffer more. An 8 B model spreads knowledge redundantly. A 1.7 B model packs it tight, so each bit lost matters more. That is why your Qwen3-1.7B dropped noticeably.
  • Below about 4 bits the error rises steeply. Q4_K_M is the usual sweet spot, Q5/Q6 are close to lossless, and Q2/Q3 break reasoning first.
  • Embeddings, attn_v and ffn_down are the most sensitive tensors, so _M mixes keep some of them at Q6_K.[40]

Smarter ways to round

  • K-quants: super-blocks of 256 weights made of sub-blocks, with quantized scales and mins. Q4_K ≈ 4.5 bpw.[39]
  • imatrix: run calibration text through the model, measure which weights matter, and give them lower error. Biggest win at Q2–Q4.
  • GPTQ: quantize column by column and adjust the remaining columns to cancel the error, using second-order (Hessian) information.[35]
  • AWQ: scale up the ~1% of channels with large activations before quantizing so they keep their precision.[36]
  • QAT: train with the rounding in the loop. Gemma 3's int4 QAT checkpoints lose far less than post-hoc Q4.[27]
  • FP8 / FP4: floating-point low precision with hardware support (H100, Blackwell). DeepSeek-V4 ships FP4 experts.[24]

06 · History

The Qwen lineage: what changed, and why

Qwen started as a LLaMA-style dense transformer and kept that skeleton for two years, scaling data instead. In 2025 it changed course: MoE with QK-Norm, then hybrid linear attention.

Aug – Nov 2023

Qwen (1.0)1.8B · 7B · 14B · 72B

Architecture
  • LLaMA-like decoder: pre-RMSNorm, SwiGLU, RoPE, untied embeddings
  • Full multi-head attention (KV heads = Q heads)
  • Bias kept only on QKV projections
  • 151,851-token BPE vocab, numbers split into digits
Why
  • LLaMA's recipe was proven, so the work went into data (up to 3 T tokens) and a vocab that compresses Chinese, English and code well
  • QKV bias helped length extrapolation. NTK-aware RoPE scaling, LogN attention scaling and window attention stretched a 2K training context further at inference time[2]
Feb – Mar 2024

Qwen1.50.5B → 110B · first MoE

Architecture
  • Same block, 32K context across the range
  • GQA only on 32B and 110B
  • Qwen1.5-MoE-A2.7B: 14.3 B total, 2.7 B active, fine-grained experts plus shared experts, upcycled from Qwen-1.8B
Why
  • A cleanup release that made the family easy to use in HF Transformers and llama.cpp
  • The MoE tested whether 2.7 B active parameters could match a 7 B dense model. It roughly could, at about ¼ of the compute per token[3][4]
Jun 2024

Qwen20.5B · 1.5B · 7B · 57B-A14B · 72B

Architecture
  • GQA in every size
  • Tied embeddings on the small models
  • Dual Chunk Attention + YaRN for 128K
  • 7 T training tokens
Why
  • GQA cuts the KV cache 4–7×, which raises long-context speed and batch capacity
  • In a 0.5 B model the 151K×896 embedding is a big share of all weights, so tying input and output embeddings saves real memory[5][17]
Sep 2024 – Jan 2025

Qwen2.50.5B → 72B · Coder · Math · 1M

Architecture
  • Essentially unchanged from Qwen2
  • 18 T tokens
  • Qwen2.5-1M added sparse attention plus DCA for million-token context
Why
  • Gains came from data and post-training, not architecture. This is the strongest evidence that the block itself was not the bottleneck[6]
Apr 29, 2025

Qwen30.6B · 1.7B · 4B · 8B · 14B · 32B · 30B-A3B · 235B-A22B

Architecture
  • QKV bias removed, QK-Norm added (RMSNorm on each head's q and k)
  • MoE: 128 experts, top-8, no shared expert, global-batch load balancing
  • 36 T tokens, 119 languages, 32K native → 128K with YaRN
  • One model with thinking and non-thinking modes
Why
  • QK-Norm stops attention logits from blowing up during large-scale training, a more principled fix than the bias
  • Balancing over the global batch instead of per micro-batch lets experts actually specialize[7][8]
Sep 2025

Qwen3-Next80B-A3B · the turning point

Architecture
  • Hybrid: 3 Gated DeltaNet layers to 1 gated full-attention layer
  • 512 experts, 10 routed + 1 shared (≈3.7% active)
  • Output gate on attention
  • Zero-centered, weight-decayed norms
  • Multi-token prediction head
Why
  • Full attention costs O(n²) compute and O(n) KV. With 75% of layers made linear, long context gets about 10× cheaper
  • The attention gate removes "attention sinks" and huge activations, which helps both stability and quantization
  • MTP gives built-in speculative decoding[9][13]
Feb – Mar 2026

Qwen3.5397B-A17B flagship · dense 0.8B · 2B · 4B · 9B

Architecture (9B config)
  • 32 layers: 24 Gated DeltaNet + 8 full attention (every 4th)
  • 16 Q / 4 KV heads, head_dim 256, partial RoPE (25% of dims)
  • 248,320-token vocab, natively multimodal
  • 262K native context, 1 MTP layer, dense MLP
Why
  • The Qwen3-Next design carried down to small models. KV is 32 KB/token versus 144 KB for Qwen3-8B, so long context fits on a laptop
  • A larger vocab means fewer tokens per sentence in 200+ languages, which is a speed win as well[10]
Apr 2026

Qwen3.635B-A3B open weights · Plus (API)

Architecture
  • Same hybrid DeltaNet + gated attention + sparse MoE family

Why

10 · Model editing

Abliteration

The "ablated" builds of Qwen in the meeting are abliterated models, which is likely the "arbitration" you meant. Abliteration removes a model's refusal behaviour by deleting a single direction from its weights. There is no retraining. It is also a clean demonstration of how concepts live inside the residual stream.

The refusal direction, in a 3-D cartoon of a 4096-D stream

drag to rotate
Copper = activations on prompts the model refuses · teal = ordinary prompts
  1. Run about 100–500 refused prompts and the same number of ordinary prompts. Record the residual stream at a middle layer.
  2. r = mean(refused) − mean(ordinary), normalized. That vector is the arrow.[41]
  3. Orthogonalize every matrix that writes into the stream (embeddings, attention out, MLP down): W ← W − r rᵀ W. Now no layer can write along r.
  4. Save the weights. The model can no longer represent "I should refuse". Everything else stays nearly untouched.[42]

The principle

Features are roughly linear directions in activation space. If a behaviour is concentrated in one direction, projecting that direction out removes the behaviour. Adding it back makes the model refuse everything.

What it costs

Small but measurable drops in benchmark scores, because r is not perfectly separate from useful features. Some authors "heal" with a short DPO fine-tune afterwards. The size stays the same, so speed is unchanged.

Use it responsibly

It removes safety training, so treat abliterated weights as unsafe for public-facing use. For your team it is useful as a hands-on lab for understanding the residual stream with HF Transformers forward hooks.

Bench plan for the Qwen3-8B baseline

Measure first, then compare each number to the Speed lab prediction. The ratio (measured ÷ predicted) tells you how much an engine or kernel change could still win.

python convert_hf_to_gguf.py ./Qwen3-8B --outtype bf16 --outfile qwen3-8b-bf16.gguf

# 2. Importance matrix from calibration text

# 3. Make each quant
for Q in Q8_0 Q6_K Q5_K_M Q4_K_M Q3_K_M Q2_K; do
  llama-quantize --imatrix imatrix.dat qwen3-8b-bf16.gguf qwen3-8b-$Q.gguf $Q
done

# 4. Speed: prompt (pp) and generation (tg) tok/s
llama-bench -m qwen3-8b-Q4_K_M.gguf -p 512 -n 128 -ngl 99 -fa 1
llama-bench -m qwen3-8b-Q4_K_M.gguf -p 512 -n 128 -ngl 0 -t 4,8,16

# 5. Quality: KL divergence vs the BF16 logits

Experiment matrix

  • Quant sweep: BF16 → Q2_K. Record file size, pp512, tg128, KLD, and "top-1 token same %". Plot speed against KLD. That curve is the trade-off you felt on 1.7B.
  • Offload sweep: -ngl 0 → 36. Speed should jump as soon as the last layer moves onto the GPU.
  • Context sweep: tg at 1K, 8K, 32K. The drop you see is the KV cache being read every token.
  • Threads sweep on CPU: find where decode stops scaling. That point is your RAM bandwidth wall.
  • Architectural A/B: Qwen3-8B vs Qwen3.5-9B vs Qwen3-30B-A3B at the same quant and 32K context. This shows dense vs hybrid-linear vs MoE.
  • Speculative: Qwen3-8B with a Qwen3-0.6B draft (-md), same output, compare tg.
For thinking models, decode speed is what mattersQwen3 in thinking mode can write 1–5K tokens before answering, so generation tok/s dominates the time you wait. Use /no_think to measure the answer-only path as well.
