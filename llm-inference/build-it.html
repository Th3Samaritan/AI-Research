2 · Structure

Anatomy of a kernel: grid → block → warp → thread

You decide how to split the work. The GPU runs a grid of blocks; each block lands on one SM and runs as warps of 32 threads that execute in lockstep.

The hierarchy, using RMSNorm as the example

  • Grid: one block per token row. A 2,048-token prefill launches 2,048 blocks; the hardware deals them out to the SMs.
  • Block: 1,024 threads sharing one SM's SRAM. They cooperate on one row of 4,096 numbers.
  • Warp: 32 threads issuing the same instruction. They can swap registers directly (__shfl_xor_sync), which is the fastest way to add numbers together.
  • Thread: each handles elements i, i+1024, i+2048, i+3072. Neighbouring threads touch neighbouring addresses, so each warp's load is one wide, coalesced memory transaction.

Analogy

The grid is the whole catering order, a block is one kitchen, a warp is a row of 32 cooks who must all do the same move at the same time, and a thread is one cook. Triton lets you write the kitchen's recipe; CUDA makes you choreograph every cook.

3 · The main design decision

Tiling: what does one program compute?

For a matrix multiply C = A·B, each program computes one BLOCK_M × BLOCK_N tile of C, walking along K in BLOCK_K chunks. The tile size decides SRAM use, how many SMs get work, and how often data is re-read.

The questions this lab answers

  • Does the tile fit? SRAM per program = stages × (BLOCK_M·BLOCK_K + BLOCK_K·BLOCK_N) × 2 bytes. Too big, and the kernel won't launch.
  • Is every SM busy? Programs = ⌈M/BLOCK_M⌉ × ⌈N/BLOCK_N⌉ × split-K. Fewer programs than SMs leaves silicon idle and memory unsaturated.
  • How full is the last wave? 130 programs on 128 SMs takes two waves, the second 2% full. That's the tail effect.
  • How much is wasted? With M = 1 (decode) and BLOCK_M = 64, 63 of every 64 rows are padding.
  • How often is data re-read? A is needed once per column of tiles and B once per row of tiles. Bigger tiles and an L2-friendly visiting order (groups of tiles that share rows and columns) keep those re-reads out of HBM.

Try these

  1. M = 1, gate_up_proj, BLOCK 64×128: 98% of the tile is padding, yet the time hardly moves. Decode is memory-bound, so wasted math is free; wasted bytes are not.
  2. M = 1, down_proj (N = 4,096), BLOCK_N = 256: only 16 programs. Raise split-K to 8.
  3. M = 4,096 (prefill), BLOCK 128×128×64, stages 4: check it fits on your GPU. On the 4090 it doesn't; on the H100 it does.

What real kernels do

Triton's @triton.autotune benchmarks a list of tile configs per shape and caches the winner. vLLM ships tuned configs for its fused-MoE kernel per GPU. Marlin uses fixed tiles designed for M ≤ 16 and splits K across SMs.

4 · Build kernel 1

RMSNorm in Triton: write → test → benchmark → (optionally) CUDA

The simplest useful kernel, and the one Qwen3 runs 73 times per token (2 per layer plus the final norm, ignoring the QK-norms). Click any numbered line to see what it does on the GPU.

Questions answered before writing it
  • Bound? Memory: 1 multiply-add per byte. Best time = bytes ÷ bandwidth.
  • What does one program do? One token row. 4,096 elements fit in registers, so the whole row is read once.
  • Minimum traffic? Read x (8 KB), write y (8 KB); the weight comes from cache. 16 KB per token.
  • Precision? Sum of squares in fp32, output in bf16, same as Hugging Face's Qwen3RMSNorm.

Step 6–7: test it against the reference, then benchmark it

# test_rmsnorm.py — the PyTorch reference is the "truth"
import torch, triton
from my_kernels.triton.rmsnorm import rmsnorm

def ref(x, w, eps=1e-6):
    xf = x.float()
    return (xf * torch.rsqrt(xf.pow(2).mean(-1, keepdim=True) + eps) * w.float()).to(x.dtype)

for tokens in [1, 7, 128, 2048, 8192]:           # decode, odd size, prefill
    for N in [4096, 5120]:                        # Qwen3-8B, Qwen3-32B (masked lanes)
        x = torch.randn(tokens, N, device="cuda", dtype=torch.bfloat16)
        w = torch.randn(N, device="cuda", dtype=torch.bfloat16)
        torch.testing.assert_close(rmsnorm(x, w), ref(x, w), atol=2e-2, rtol=2e-2)

x = torch.randn(8192, 4096, device="cuda", dtype=torch.bfloat16); w = torch.ones(4096, device="cuda", dtype=torch.bfloat16)
ms = triton.testing.do_bench(lambda: rmsnorm(x, w))             # median time in ms
gbs = 2 * x.numel() * x.element_size() / ms / 1e6                # read x + write y
print(f"{ms*1e3:.1f} µs, {gbs:.0f} GB/s")                        # compare with your GPU's peak
ms_eager = triton.testing.do_bench(lambda: ref(x, w))           # unfused PyTorch baseline

5 · Build kernel 2

Fused SiLU × mul: what fusion buys, in bytes

SwiGLU computes silu(gate) * up. vLLM's SiluAndMul does it in one kernel over the fused gate_up output, whose first half is gate and second half is up.

@triton.jit
def silu_mul_kernel(GU, Y, N, BLOCK: tl.constexpr):
    row, blk = tl.program_id(0), tl.program_id(1)    # 2-D grid: token × chunk
    cols = blk * BLOCK + tl.arange(0, BLOCK)
    m = cols < N
    g = tl.load(GU + row * 2 * N + cols,     mask=m).to(tl.float32)   # gate half
    u = tl.load(GU + row * 2 * N + N + cols, mask=m).to(tl.float32)   # up half
    y = g * tl.sigmoid(g) * u                          # silu(g) * u, in registers
    tl.store(Y + row * N + cols, y.to(Y.dtype.element_ty), mask=m)

def silu_mul(gu):                                      # gu: [tokens, 2N]
    T, N = gu.shape[0], gu.shape[1] // 2
    y = torch.empty(T, N, device=gu.device, dtype=gu.dtype)
    silu_mul_kernel[(T, triton.cdiv(N, 1024))](gu, y, N, BLOCK=1024)
    return y

Why the grid is 2-D

N = 12,288 for Qwen3-8B. One program per row would give only 1 program for a decode step, on a GPU with 128 SMs. Splitting each row into 1,024-wide chunks gives 12 programs for one token and 24,576 for a 2,048-token prefill.

Questions to ask

  • Unfused: F.silu(g) writes a temporary, and * u reads it back. How many bytes is that per token?
  • When does fusion matter most? When the op runs on many tokens (prefill), or when launch overhead dominates (decode without CUDA graphs).

6 · Build kernel 3 · your quantization kernel

A 4-bit weight × 16-bit activation GEMV (W4A16), from scratch

This is what Marlin and llama.cpp's Q4 kernels do at heart: keep the weights packed in HBM, unpack and dequantize them in registers, and multiply. Decode reads 4× fewer bytes, so it can run up to about 4× faster.

The format: 8 weights per 32-bit word, one scale per group of 128

Pick which of the 8 nibbles to unpack. Row k of the weight lives in word k // 8, at bit offset (k % 8) × 4.

Why it's faster: bytes for one Qwen3-8B layer's gate_up_proj

Design questions, answered
  • What does one program compute? BN = 64 outputs for one token, looping over all of K. Grid = (N / 64, tokens) = 384 programs for gate_up, about 3 per SM on a 4090.
  • Where does dequantization happen? In registers, right after the load. The bf16 weights never exist in memory.
  • Why fp32 accumulation? 4,096 products summed in fp16 lose about 3 significant digits.
  • What's deliberately simple? Each 32-bit word gets loaded 8 times (the extra 7 hit L1). A tuned kernel loads it once and unpacks all 8. That's iteration 2, after this version passes its tests.

Quantize, test, benchmark

# reference quantizer + dequantizer: slow, obviously correct
def quantize_w4(W, group=128):                         # W: [K, N] float → packed int32 [K/8, N], scales [K/G, N]
    K, N = W.shape
    Wg = W.float().view(K // group, group, N)
    s = (Wg.abs().amax(dim=1) / 7).clamp(min=1e-8)     # symmetric: map max |w| to 7
    q = (torch.round(Wg / s[:, None]) + 8).clamp(0, 15).to(torch.int32).view(K // 8, 8, N)
    qw = torch.zeros(K // 8, N, dtype=torch.int32, device=W.device)
    for j in range(8):
        qw |= q[:, j, :] << (4 * j)                      # nibble j of each word = row 8·i + j
    return qw, s.half()

def dequant_w4(qw, s, group=128):
    shifts = torch.arange(0, 32, 4, device=qw.device, dtype=torch.int32)
    q = (qw[:, None, :] >> shifts[None, :, None]) & 0xF  # [K/8, 8, N]
    return (q.reshape(-1, qw.shape[1]).float() - 8) * s.float().repeat_interleave(group, dim=0)

K, N = 4096, 24576                                      # Qwen3-8B gate_up_proj
W = torch.randn(K, N, device="cuda") * 0.02
qw, s = quantize_w4(W)
x = torch.randn(1, K, device="cuda", dtype=torch.float16)
ref = (x.float() @ dequant_w4(qw, s)).half()             # compare against the DEQUANTIZED weights:
torch.testing.assert_close(w4a16_gemv(x, qw, s), ref, atol=2e-2, rtol=1e-2)   # kernel error, not quant error

Wh = W.half()
ms_w4   = triton.testing.do_bench(lambda: w4a16_gemv(x, qw, s))
ms_fp16 = triton.testing.do_bench(lambda: x @ Wh)                              # cuBLAS baseline
bytes_w4 = qw.numel() * 4 + s.numel() * 2 + x.numel() * 2 + N * 2
print(f"W4: {ms_w4*1e3:.0f} µs ({bytes_w4/ms_w4/1e6:.0f} GB/s) · FP16: {ms_fp16*1e3:.0f} µs")
Two different errors. Keep them apart.

Kernel error (does my kernel compute what the format says?) is tested against the dequantized reference with tight tolerances. Quantization error (does 4-bit hurt the model?) is measured with perplexity and lm-eval on the whole model (Part 5, section 11). Mixing them hides kernel bugs inside "quantization noise".

7 · Verdict

Is my kernel good? Achieved bandwidth vs the roofline

Enter what do_bench printed. Memory-bound kernels are judged by achieved GB/s as a share of peak, compute-bound ones by TFLOP/s.

Rules of thumb

  • Above 80% of peak bandwidth: done. Move on to the next bottleneck in the profile.
  • 50–80%: tune. Try other tile sizes with autotune, vectorize loads (128-bit), add split-K if there are few programs.
  • Below 50%: something structural. Check uncoalesced access (a strided or transposed layout), too few programs, register spills (ncu: "local memory"), or the launch overhead on tiny inputs.
  • Tiny inputs (under ~10 µs): you're measuring launch overhead. Benchmark inside a CUDA graph, or judge the kernel at realistic sizes.

Profile commands

ncu --set full -k regex:w4a16 -o w4 python bench_w4.py   # one kernel, every counter
# look at: Memory Throughput %, Achieved Occupancy, Warp Stall reasons, L1/L2 hit rate
nsys profile -o step python serve_one_step.py              # whole step: which kernels, gaps between them

10 · Application

Extending vLLM: your kernel, your format, your model

vLLM is built to be extended from outside: a pip package with an entry point gets loaded into every vLLM process. You don't need to fork it to add a quantization method or a model.

a · Wrap the kernel as a PyTorch op

So torch.compile and CUDA graphs can trace it. The fake implementation tells the compiler the output shape without running the GPU code.

# my_kernels/ops.py
@torch.library.custom_op("my_kernels::w4a16_matmul", mutates_args=())
def w4a16_matmul(x: torch.Tensor, qw: torch.Tensor, s: torch.Tensor, group: int) -> torch.Tensor:
    x2 = x.reshape(-1, x.shape[-1])
    if x2.shape[0] <= 4:                                   # decode: memory-bound → your GEMV
        y = w4a16_gemv(x2, qw, s, group)
    else:                                                  # prefill: compute-bound → dequantize once, cuBLAS
        y = x2 @ dequant_w4(qw, s, group).to(x.dtype)
    return y.view(*x.shape[:-1], qw.shape[1])

@w4a16_matmul.register_fake
def _(x, qw, s, group):
    return x.new_empty(*x.shape[:-1], qw.shape[1])

b · Register a quantization method

The config class reads the checkpoint's quant config; the method class creates the packed parameters (so the loader can fill them) and calls your op in apply. A skeleton: compare it with gptq.py in your vLLM version, because weight-loader attributes change between releases.

# my_quant/vllm_plugin.py
import torch
from vllm.model_executor.layers.quantization import register_quantization_config
from vllm.model_executor.layers.quantization.base_config import QuantizationConfig
from vllm.model_executor.layers.linear import LinearBase, LinearMethodBase
from vllm.model_executor.utils import set_weight_attrs
from my_kernels.ops import w4a16_matmul

@register_quantization_config("my_w4")
class MyW4Config(QuantizationConfig):
    def __init__(self, group_size=128):
        super().__init__(); self.group_size = group_size
    def get_name(self): return "my_w4"
    @classmethod
    def get_supported_act_dtypes(cls): return [torch.float16, torch.bfloat16]
    @classmethod
    def get_min_capability(cls): return 80                  # Ampere and newer
    @staticmethod
    def get_config_filenames(): return ["quantize_config.json"]
    @classmethod
    def from_config(cls, cfg): return cls(cfg.get("group_size", 128))
    def get_quant_method(self, layer, prefix):
        return MyW4LinearMethod(self) if isinstance(layer, LinearBase) else None

class MyW4LinearMethod(LinearMethodBase):
    def __init__(self, cfg): self.cfg = cfg
    def create_weights(self, layer, input_size_per_partition, output_partition_sizes,
                       input_size, output_size, params_dtype, **extra):
        K, N, G = input_size_per_partition, sum(output_partition_sizes), self.cfg.group_size
        qweight = torch.nn.Parameter(torch.empty(K // 8, N, dtype=torch.int32), requires_grad=False)
        scales = torch.nn.Parameter(torch.empty(K // G, N, dtype=params_dtype), requires_grad=False)
        set_weight_attrs(qweight, {"input_dim": 0, "output_dim": 1, "packed_dim": 0, "pack_factor": 8, **extra})
        set_weight_attrs(scales, {"input_dim": 0, "output_dim": 1, **extra})
        layer.register_parameter("qweight", qweight)
        layer.register_parameter("scales", scales)
    def apply(self, layer, x, bias=None):
        y = w4a16_matmul(x, layer.qweight, layer.scales, self.cfg.group_size)
        return y if bias is None else y + bias

def register():          # entry point: importing this module ran the decorator above
    pass
# pyproject.toml — vLLM loads every "vllm.general_plugins" entry point in every process
[project.entry-points."vllm.general_plugins"]
my_w4 = "my_quant.vllm_plugin:register"

# then
pip install -e .
vllm serve ./qwen3-8b-my-w4 --quantization my_w4

# register your own class for an architecture name (in the plugin's register())
from vllm import ModelRegistry
ModelRegistry.register_model("MyQwen3ForCausalLM", "my_pkg.qwen3_custom:MyQwen3ForCausalLM")
Check before you trust it
  • Model: same prompts through HF Transformers and vLLM at temperature 0. The first 32 generated tokens should match, and logits should be within bf16 noise.
  • Quant method: perplexity within your tolerance of the GPTQ/AWQ baseline, then vllm bench serve vs the Marlin path.
  • CUDA graphs: run once with --enforce-eager and once without. Identical outputs prove your op is graph-safe: no host sync, no allocation that depends on data.

12 · Test & ship

Testing and shipping checklist

Correctness tolerances

dtypetorch default rtol / atolKernel tests in practice
fp321.3e-6 / 1e-5default
fp161e-3 / 1e-5≈1e-2 / 1e-2
bf161.6e-2 / 1e-5≈2e-2 / 2e-2
int4 / fp8 weightscompare with the dequantized reference in fp32, never with the original weights

Fast kernels add numbers in a different order than the reference, so exact equality is the wrong test. If a test only passes with a loose atol, check the error grows with K (an ordering effect) rather than being random (a bug).

The checklist

  1. Shapes from the real model, plus edge cases: 1 token, an odd count (7), the largest batch, N not a power of 2.
  2. Both dtypes you serve (fp16, bf16), and non-contiguous inputs if callers can pass them.
  3. Fixed random seeds; values with outliers (×100 in a few channels), like real activations.
  4. Microbenchmark in CI with a threshold such as "≥ 70% of peak bandwidth", so a regression fails the build.
  5. Graph safety: eager vs CUDA graphs give identical outputs.
  6. Whole-model checks: perplexity, lm-eval, and greedy outputs vs HF.
  7. Serving benchmark: vllm bench serve rate sweep against the baseline, then report goodput at your SLO.
